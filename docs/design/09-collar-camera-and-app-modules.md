## 2. 为什么之前会"瞬移"（第 ③ 条的病因）

`planTravel()` 里算的是**真实秒**：一次 3 m 的横穿约 3 秒（`flat / walkSpeed + 余量`，上限 12 秒）。
但运行时的推进量取的是 `this.t - planStartT`——**时间线秒**，而时间线在 20× 倍率下走得飞快：

```
计划 3.0 真实秒的走路 → 实际在 0.15 秒内走完 → 肉眼就是瞬移
```

这条 bug 与 stage2 §7.5 记录的那次修复**同源但不同处**：当时修的是"位移时长不该取时间线时长"，
这次修的是"位移的**推进量**不该取时间线秒"。两个量都对了，走路才真的看得见。

### 三条规则

| 规则 | 内容 |
|---|---|
| **1. 真实秒推进** | 位移按 `planElapsedS += step`（真实秒）推进，与 `planTravel` 给的真实时长同一把尺子 |
| **2. 时间线局部刹车** | 走路时把时间线速率压到 `min(timeScale, 剩余时间线秒 / 剩余真实秒)`——**走完这段正好用完这段位移的时间线时长**。因此不瞬移、也不落后于时间线、标签不会与画面矛盾 |
| **3. 段切换按需重规划；跳跃例外** | 位移段一定规划；**非位移段而猫不在该锚点上**也规划（这条专治"时间线直接在两个锚点之间切换"的瞬移）；普通走路目标变了就从**当前位置**重新规划（轨迹连续），而**高度差超过跳跃门限**时按跳处理，可以直接改目标——这就是用户要的"只有跳跃可以忽略轨迹" |

**刹车的代价**（实测，`--seed 42/7`）：一天的位移段占 5.5–6.7%，中位时长约 21 时间线秒（在 20× 下只值 1.05 真实秒），
而按真实步速走需要约 2.5 秒——每段补 1.5 秒左右，全天补约 4–5 分钟。**一场演示从约 72 分钟变成约 76–77 分钟**，
换来的是每一次走动都看得见。这个交换在演示场景里是明显划算的。

另外两处顺带修掉：
- 运行中**换时间线**（注入突发、改档案）时不再瞬间落到新锚点上：`applyTimeline` 会把猫当前变换传进去，
  若不在新锚点上就**走过去**（`startTransform` + `plannedArrival`）。
- 走路期间状态标签显示「移动」而不是时间线那一段的名字——**标签必须与画面一致**。

## 3. 项圈相机（第 ① 条）

- **几何**：带体前端一颗小镜头（`collar-camera`），项圈部件数因此从 5 变 6（自检断言同步更新）。
- **机位锚点**：`CatRig.povAnchor` 放在带体前端稍前处、朝 +Z。挂在 `body` 上，因此自然跟着猫的身体与朝向走。
- **机位预设**：`项圈相机`（`?view=collar-cam`）把主相机放到镜头上，每帧跟随。
- **渲染时隐藏猫自己**：真实项圈相机拍不到自己的后脑勺；不隐藏的话画面里全是毛与胡须壳。

**措辞边界（硬约束）**：这是**环境影像**。界面与文档一律不说「宠物视角 / 还原宠物所见」——
帧率（猫 CFF 约 58 Hz）、视野、色觉与嗅觉通道都不等价（`AGENTS.md` §3）。机位 hint 里原样写了这句边界。

## 4. App 四模块（第 ② 条）

| 模块 | 内容 | 取数 |
|---|---|---|
| **实时** | **项圈相机画面**（便于判断它在哪）+ 它现在在做什么 / 在哪 | 场景离屏渲染 + 场景状态 |
| **事件流** | 每 **5 分钟**一条记录（可滚动，机身高度不变）+ 喝水/进食/玩耍/用砂盆/抓挠/躲藏**次数与时长** | `behaviorTimeline.segments` + `events` |
| **健康** | 心率 / 呼吸频率 / 体表温（**从实时页挪过来**）+ 异常标红 + 弹窗 + 相对前半段基线的漂移 | `samples` + `core/vitals/alerts` |
| **档案** | **可选**品种与年龄，及其推导出的年龄段 / 体型档 / 项圈重量预算 / 颈围带长 | `core/profile` 的 `CAT_BREEDS` 与 `AGE_OPTIONS_MONTHS` |

几处刻意的选择：

1. **事件流每 5 分钟一条**（按用户要求），内容是"这 5 分钟**主要在做什么** + 事件数"，
   而不是逐条事件流水——逐条流水在 20× 演示下每几秒滚一大片，读不出重点。
2. **列表自身滚动**（`.app-scroll` + `max-height` 双保险），机身高度由 `aspect-ratio` 定死，再长也不撑高。
3. **次数统计只统计"已经发生过"的区间**（`seg.t + seg.durS <= tNow`），不把未来的计划算进去。
4. **品种表标 `weak`**：品种体型是公开资料的概略值，本仓库**未取得同行评审一手来源**；
   它的用途只有一个——让"换品种 → 基线跟着变"在仿真里成立。
5. **换品种/年龄会按新档案重建整段会话**（同一种子，并把场景时间线换到同一份上，`applyTimeline` 从当前时刻继续）。
   因此读数基线会跟着变，而这**就是**档案的作用：档案驱动的是"这只猫自己的基线"，不是种群平均值。

## 5. 自检：两个新仪器

浏览器侧的事实无法单测（要 three + 控制器 + DOM），因此本轮加了两个**可断言的仪器**：

| 仪器 | 怎么用 | 断言什么 |
|---|---|---|
| **位移探针** `startMotionProbe(秒)` | 记录接下来 N 秒的**逐帧位置**，算出最大瞬时速度 / 最大单帧位移 / 移动帧占比 / 位置取值个数 | `maxSpeedMps < 6`（走速约 0.45、跳跃弧顶几 m/s；**瞬移会是每秒几十米**）、`distinctPositions ≥ 3`（确实有轨迹，不是只有起终点） |
| **项圈相机帧计数** `povState()` | 「实时」模块挂上画布后场景才创建渲染目标并累计帧数 | `bound === true` 且 `frames > 0`——防"挂了一块空画布" |

自检序列（`?debug=1&auto=1`）现在依次覆盖：切档位 → 收起/展开 App → **位移探针** → 注入抽搐 →
项圈与无干涉区 → 事件流 / **健康** / 档案 → **换品种（缅因猫）** → 回实时。

```bash
node scripts/dev-server.mjs
chrome --headless=new --use-angle=swiftshader --enable-unsafe-swiftshader \
       --virtual-time-budget=45000 --window-size=1280,860 \
       "http://127.0.0.1:5273/?debug=1&auto=1"
node scripts/smoke-scene.mjs
```

新增/更新的断言：四个模块可切换 · 事件流渲染出 5 分钟记录 · **行为次数统计字段存在** ·
档案换品种生效 · 项圈部件数 = **6**（含摄像头）· 项圈相机绑上并渲染出帧 · **没有瞬移且确实有轨迹**。

## 6. 已知限制

1. **项圈相机画面是 176×132、约 8 fps**：每次都要把像素从 GPU 读回 CPU，代价不小；分辨率与帧率都为此让步。
   它够用来判断"它在哪、周围有什么"，不够用来看清细节。
2. **画面里没有猫自己**（渲染时隐藏）。这与真实项圈相机的视角一致，但也意味着它**不能**用来自证姿态。
3. **走路刹车会让演示变长**（约 72 → 76 分钟）。若某天更要紧的是"一场演示更快走完一天"，
   可把刹车改成"只在目标距离超过 N 米时才刹车"，代价是近距离移动仍会显得快。
4. **品种体型取值是概略值**（`weak`），改品种只影响仿真基线与展示，不代表任何个体。
5. **事件流的 5 分钟粒度**意味着短事件（一次 20 秒的干呕）只会体现在"事件数"里，不单独成条。
6. 位移探针的阈值（6 m/s）是**工程判据**：它拦的是"两帧之间跨了房间"，不是"走得比猫快"。

## 7. 第六轮反馈：四个"界面故障"的根因与修法

用户报的四条里，有三条其实是**同一个 bug**：整块重建 DOM。

| 反馈 | 根因（都不是"样式没调好"） | 修法 |
|---|---|---|
| ① 档案页品种/年龄**点开就马上关闭** | 每 500 ms 把 `.app-body` 整个 `replaceChildren` 一遍 → **`<select>` 刚展开就被销毁** | 模块**建一次 + 就地刷新**（`TabView`）；焦点在模块内时**跳过刷新** |
| ③ 事件流/健康/档案内容一多，**iPhone 被撑长** | 一是 DOM 重建把滚动位置清零（"滑不动"）；二是 `.phone` 只给了 `aspect-ratio`，而 flex 子项的 `min-height: auto` 会被内容顶大，**压过**宽高比推出来的高度 | 机身高度**写成确定值**（`height: min(calc(--phone-w * 19/9), 68vh)`）+ `.app-body { flex: 1 1 0; min-height: 0; overflow-y: auto }` 成为**唯一**滚动容器；刷新时保留 `scrollTop` |
| ④ 项圈相机**画面闪动** | 每 500 ms 换一块新画布 → 场景反复重建 `WebGLRenderTarget`，首帧未填充就显示 | 画布**只建一次**；渲染目标**尺寸不变就复用**；顺带把 6 → **8 fps**，并给机位加一阶平滑抑制姿势微动 |
| ② 删掉左栏「项圈相机高度 0.20 m」 | 那是一个**固定世界机位**：猫一走开，它就与猫无关了 | 删除该预设；保留跟随镜头的「项圈相机」。推导函数 `cameraHeightOf()` 留在 core（规格表仍在用，且有单测） |

### 7.1 顺带把"视角高度与猫一致"变成可核对的数

镜子（镜头）挂在项圈的机位锚点上，锚点高度取**猫自己的眼高**：
`body` 空间的 `0.05` 加上站姿的 `bodyLift ≈ 0.15` → 离它脚下的表面约 **0.20 m**，正是颈高量级，
并且跟着姿势走（趴下时镜头跟着降低，不会悬在半空）。

自检因此能直接断言这个数：`catPov.eyeHeightM ∈ (0.1, 0.45)`——0 说明锚点没挂上或世界矩阵没更新，
过大说明镜头飘在半空。**高度不再靠肉眼判断。**

### 7.2 尺寸类故障靠"量"而不是靠"看"

`app.layout` 把机身高度与滚动高度写进快照：`phoneHeight` / `bodyClientHeight` / `bodyScrollHeight` / `canScroll`。
断言有两条，缺一不可：

- 各模块之间 `phoneHeight` 的差 **≤ 2 px**（机身不会被内容撑长）；
- 内容最长的模块 `canScroll === true`（内容真的在机身内滚，而不是溢出）。

肉眼看截图**分不出**"手机变长了"与"内容滚动了"，这两条断言补的正是这个盲区。
用户反馈里"点开就关闭"这类交互故障也同理：断言下拉的**选项数量**（12 个品种 / 7 个年龄档），
被反复销毁的空壳会立刻暴露。
