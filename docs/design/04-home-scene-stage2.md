# 04 · 猫的行为建模（第二阶段）

> **状态**：已实现。核心/仿真/前端三层门禁全绿；场景自检需人在普通终端跑一次（见 §8）。
> **范围**：让猫从「两套手动演示档位」升级为**由可验证真值驱动的自主行动个体**，
> 并支持本地手动触发一次**突发动作演示**。

## 2. 三层行为模型（为什么不是单层状态机）

任何时刻的猫 = **三条互相独立的轴**叠加，突发是第四条覆盖层：

| 轴 | 取值 | 谁决定 |
|---|---|---|
| **姿势** `CatPosture` | `lying` / `sitting` / `standing` / `crouching` / `walking` / `climbing` | 行为状态 |
| **行为状态** `CatActivityId` | `resting` / `alert` / `grooming` / `locomoting` / `playing` / `feeding` / `drinking` / `eliminating` / `scratching` / `hiding` / `perching` / `vomit` | 节律 + 计时器 + 事件 |
| **位置锚点** | 17 个具名锚点（`CAT_ANCHOR_IDS`） | 状态转换时选定；位移由 web 层执行 |
| **突发** `CatIncidentKind` | `seizure` / `labored-breathing` / `freezing` / `withdrawal` / `vomit` | 用户手动触发或仿真注入；有固定时长 |

**为什么这样切**：
- 现有 `cat-states.ts` 的 `CatPoseParams` 是**渲染参数**（耳位、瞳孔、尾频），属于表现层。
  行为层只输出**语义化的 activity + posture**，由表现层翻译。若把「尾巴 2.4 Hz」当行为模型，
  行为就再也无法脱离 three.js 单测。
- 位置与行为解耦：行为引擎只说「去哪、干什么」，寻路与动画在 web 层。
  因此**行为引擎可以在没有浏览器、没有 three.js 的环境下单测**。

## 4. 三条不变量（时间线为什么必须满足）

1. **连续覆盖**：`segments` 首尾相接、无空洞、无重叠，`Σ durS === durationS`。
   有了这条，`activityAt(t)` 才有唯一正确答案，回归断言也才有判据。
2. **不依赖 wall clock**：引擎是纯数据，画面推进由 `apps/web` 按 wall clock 做
   （沿用第一阶段踩过的坑：逐帧累加会在后台降帧时卡住）。
3. **突发是覆盖层**：注入一次突发只是在行为之上叠加一段带 `incidentKind` 的区间，
   并标记 `injected: true`，让「注入 → 还原」可被断言。

**一个实现细节值得记下**：躲藏退避（`withdrawal`）需要先走到躲藏点，
若「走完再开始计时」，注入时刻会被路程整体后推（实测 11–14 秒），
`注入 → 还原` 的断言随之失效。做法是**先把时间轴裁到 `事发时刻 − 路程`**（`rewindTo`），
再走一次贴地位移，使「到达」与「事发」落在同一时刻。因此注入时刻与落位时刻
的偏差被限制在 1 秒内（引擎刻意在事发前 1 秒结束前一个片段，
避免画面「先跳到事发动作再看它开始」）。

## 5. 证据政策如何落到代码里

| 政策 | 执行点 |
|---|---|
| `unverified` 不得展示具体数值 | `BehaviorParam.value` 恒为 `null`；`behaviorParamText()` 对 `unverified` 返回「未取得可靠来源」；单测断言其展示文本不含数字 |
| `disputed` 必须展示为区间 | `value` 必须是二元数组（或写明「无法归因」） |
| 每个参数带证据等级 | `BEHAVIOR_PARAMS` 每项必带 `EvidenceTag`（tier/source/note） |
| 操作化常量不得冒充文献数字 | `OPERATIVE_CONSTANTS` 单列一张表，每项必须写明「为什么这么选」 |
| 措辞纪律 | 行为层全部面向用户的文案进 `FORBIDDEN_TERMS` 单测；断言复刻门禁的**行级否定标记**规则 |

**当前登记表里的 4 处 `disputed`**：
24 小时节律稳健性、发声能否作为独立征象、长时间不动能否归因、
静息心率与呼吸频率（都是语境冲突，必须带测量条件）。
**12 处 `unverified`** 包括：每日跳数、活动片段数与时长、抓挠单次时长、
饮水量、排尿/排粪次数、躲藏时长占比、垂直空间占比、主人不在时活动量/抓挠/躲藏的方向。

**明确不做**：
- 不建模情绪或感受（`vocabulary.ts` 里没有任何情绪取值——不是遗漏，是设计）；
- 不给疾病名称（5 个突发动作全部是**动作名**）；
- 不做声音语义翻译（发声只作「有声/无声」计数）。

## 6. 突发演示：动作语义与渲染

| kind | 画面上是什么 | 演示时长 | 渲染做法 |
|---|---|---|---|
| `seizure` | 倒卧、全身与四肢高频抖动 | 15 s | 11 Hz 抖动（幅度约躯干高的 50%）+ 四肢错相位抽动 + 躯干随机偏转 |
| `labored-breathing` | 蹲伏不动、头部前伸、呼吸幅度与频率明显升高 | 60 s | 呼吸幅度 +0.016 m（受 0.05 m 上限约束）、频率 2.6× |
| `freezing` | 长时间完全不移动（仅保留眨眼与呼吸）、弓背、头低垂、耳后压 | 60 s | 抖动为 0、僵直 1.0（四肢绷直拉长）+ 更慢更浅的呼吸 |
| `withdrawal` | 迅速移动到躲藏点、随后不再出现在开阔处 | 90 s | 走 `hiding` 活动 + 躲藏锚点；到位后僵直 0.6 |
| `vomit` | 前低后高的「祈祷」姿态、腹部反复起伏 | 30 s | 2.2 Hz 躯干俯仰起伏 + 腹部抽动 |

**突发必须有身体动作，不能只换姿势** ⚠️

这是实现过程中真实踩到的坑：第一版突发只把活动换成 `resting`/`hiding`、姿势换成普通
趴卧/蹲伏，**没有任何身体动作**。结果是标签写着「抽搐」而猫只是趴着不动——
用户点下去观感就是「没反应」。修法是在每个突发上挂一套 `IncidentMotion`：

| 通道 | 作用 | 谁主要靠它 |
|---|---|---|
| `tremorAmp` / `tremorFreq` | 躯干与头部高频抖动 | `seizure`（11 Hz，约为呼吸的 26 倍） |
| `limbJitter` | 四肢抽动（每条腿相位错开，避免整齐划一读成「机械」） | `seizure` |
| `bodyTwist` | 躯干随机偏转 | `seizure` / `vomit` |
| `breathAmpAdd` / `breathFreqScale` | 呼吸幅度与频率 | `labored-breathing` |
| `rigidity` | 肌肉僵直（四肢绷直、身体拉平） | `freezing`（1.0） |

**两个反直觉的取舍**：

1. **`freezing` 不能靠动作表达。** 它要传达的恰恰是「长时间静止」，
   所以抖动为 0，只能靠**僵直 + 更慢更浅的呼吸**与「放松趴着」区分。
   单测专门断言 `freezing` 与 `seizure` 的表达方式相反——
   否则哪天有人给 `freezing` 也加上抖动，它就退化成第二个「抽搐」。
2. **呼吸幅度用「叠加量」而不是「倍数」。** 基准 `breathAmp` 只有 0.028–0.034 m，
   一开始写成 3.4 倍，算出 116 mm 的胸廓起伏（体长仅 300 mm）——那是**猫在膨胀**，
   不是「在喘」。改成叠加 +0.016 m，并在渲染层加了 `MAX_BREATH_AMP = 0.05 m` 的
   视觉安全线（突发配方再大也越不过它）。

**演示时长是「给人看的真实秒数」，不乘演示倍率**：真实时长与它差别很大
（「僵直不动」在文献描述里可以是十分钟量级），这里刻意压缩到 10–90 秒，
让用户点一下就能看完整段；渲染层对突发段按**真实时间**推进（见 §7.5）。
这一点在界面上以「动画演示」措辞说明，并由单测把可用的时长区间钉住。

**常驻文案**（不可改写，来自 `core` 的 `INCIDENT_BOUNDARY_NOTE` / `INCIDENT_REFERRAL_NOTE`）：

> 突发演示：以上是你手动触发的动画演示，不是系统对猫的感受、情绪或身体状况的识别，
> 也不构成任何诊断。若你的猫真的出现类似表现，请录像并联系兽医。
>
> 以下情形在权威兽医资料中列为需要尽快就诊：张口呼吸或呼吸费力、公猫反复蹲砂盆却排不出尿、
> 反复呕吐、食欲下降持续三天以上。请录像并联系兽医，不要等待。

## 6.5 头顶状态标签：把行为模型外显

**为什么加这个**（这是设计判断，不是装饰）：动画天生难以表达「抽搐」「呼吸急促」
「用猫砂盆」这类动作——它们在画面上都只是「猫在动」。而本项目的交付面本来就是
**行为层**，不是写实动画。把当前行为与突发状态直接标在猫头顶，等于把内部模型外显，
演示时观众不需要猜「它现在是在抓挠还是在抖」。

实现要点（`cat-status-label.ts`）：

| 事项 | 做法与理由 |
|---|---|
| DOM 宿主 | **独立于资源标签层**。资源标签那层有「近处优先 + 相互遮挡就隐藏」的贪心去重（避免十几个锚点标签糊成一团），猫的状态标签只有一条，绝不能因为撞上某个资源标签就被隐藏 |
| 文案节流 | 只在内容真的变了才改 `textContent`；每帧改会让文字反复重排，低端设备上肉眼可见地抖 |
| 位置 | 每帧投影（猫在动），偏移取猫根节点上方 0.34 m |
| 越界 | 猫跑出画面或到相机背后时隐藏，避免标签贴在屏幕边缘误导「它在那」 |
| 突发配色 | 突发期间切成醒目配色并加圆点，因为那一刻最该被看到的就是「发生了什么动作」 |
| 措辞 | 文案取自 `@camp/core` 的行为/突发词汇表，本文件不另写一套；只描述**可观察的行为与动作**，不出现感受、情绪或疾病名称 |

**默认开启**，因为它是主线信息；`?status=off` 或「图层与画质」里的
「显示猫头顶的状态」可关掉（截图时经常需要干净画面）。
它与「显示资源标签」是**两个独立开关**——演示时经常需要「关掉满屋标签、只看猫」。

### 6.6 为什么标签一开始「看起来不更新」（反馈节奏问题）

用户反馈「动作看得到、但标签文字不变」。查证后**标签逻辑本身没有 bug**，
是**反馈节奏**三处叠加造成的错觉。这个坑值得完整记下来，因为它不是靠读代码能发现的：

| 现象 | 实测数据 | 原因 |
|---|---|---|
| 长时间显示同一个名称 | `resting` 段平均 **56 秒**、16 段超过 **60 秒**（最长约 2 分钟） | 整段里活动名与姿势都不变，文字「确实没变」 |
| 「移动」几乎看不到 | `locomoting` 段平均 **1.2 秒**、最短 **0.2 秒** | 比刷新节流还短，来不及显示就进下一段 |
| 刷新太粗 | `emitStatus` 按 **250 ms** 节流 | 节流间隔比最快的段还长，短段被整段吞掉 |

**三处修改**：

1. **行为运行时改为逐帧推送，节流下沉到消费方**。`locomoting` 短到 0.2 秒，
   任何粗于它的节流都会把它吞掉。现在：头顶标签只在**内容变化**时改文本、
   按 **1 秒**改进度计数；HUD 面板另按 1 秒节流（它只是一行字）。
   修前 90 秒只收到 **1 个**状态，修后收到 **8 个**。
2. **标签加段内进度计数**（`本段 12s`）。这是让「长时间不变的活动名」也看得出
   **时间在走**的关键——否则 `resting` 段里两分钟一动不动，任何用户都会以为卡住。
   计数按**真实秒**而不是时间线秒：时间线秒在 20× 下每次跳 20，看起来像坏了。
3. **HUD 面板同样显示段内进展**，并附所在位置。

**诊断方法上的一个教训**：我第一次验证时写了个脚本模拟 90 秒，结果只收到 1 个状态，
差点判定「绑定坏了」。实际上脚本在**真实时间**里只跑了几十毫秒，而节流用的是真实时间——
所以"只收到 1 个"是测试方式的假象，不是代码的故障。
**用真实时间做节流的东西，不能靠在真实时间里瞬间跑完的脚本去验证。**
后来把诊断改成逐帧推送后立刻看出 8 个状态变化。这条记在这里，免得下次再踩。

**自检怎么断言**：不靠「标签文案有没有变」（`resting` 段里本来就不变），
而是断言**段内进展计数在推进**或**已切换到新段**——这才是「时间线在走」的可靠证据。

## 7. 房间锚点与可达性

- **权威坐标仍是 `layout.ts`**。`anchor-map.ts` 只做映射，不新增坐标。
- **锚点 id 是跨包契约**：单一事实来源是 `@camp/core` 的 `CAT_ANCHOR_IDS`；
  `simulator` 与 `apps/web` 各建一张表，core 单测断言两张表的 id 集合与契约一致。
  （这条断言在实现时立刻抓出了一次真实的不一致——测试夹具用了 `food`/`water` 这类临时 id。）
- **跳跃图由高度差决定**：高度差 > `jumpMinHeightM`(0.15 m) 走攀跳弧线，否则贴地走。
- **不引用「最大跳跃高度」数字**（该项 `unverified`）：可达性只由房间实际台面高度约束，
  最高的猫用台面是衣柜顶 2.4 m，记在 `anchorVerticalReachM` 并写明理由。
- **资源点停在物件前方**而不是中心，否则猫会站进碗里或砂盆里。
  地面锚点全部经静态检查（在房间内、不压家具）。

**已知限制**：没有寻路算法，位移是直线 + 弧线。样板间是单间且空旷，
直连在视觉上成立；换到多房间平面时这一层需要替换为网格寻路。

## 7.5 演示节奏：两个互相冲突的目标，以及怎么解开

第一版跑起来之后立刻暴露了一个观感问题：**猫会从一个位置「闪」到另一个位置**，
而且完全看不到喝水、吃粮、用猫砂盆。查下来三个现象是同一个根因——
**演示倍率把一切都压扁了**：

| 环节 | 第一版 | 结果 |
|---|---|---|
| 演示倍率 | 60× | 一次进食的时间线时长折算到真实时间只有约 **0.5 秒** |
| 位移动画时长 | 直接取时间线片段长度 | 一次移动只有 **0.3–3 秒** → 读成瞬移 |
| 吃喝/排泄的权重 | 与其它行为同量级 | 各仅占约 **2%**，且一闪而过 |

**关键判断：位移时长必须与时间线时长解耦。** 否则「一场演示看完一天」与
「看清猫在走路」在数学上无法同时满足——要么猫瞬移，要么一天永远走不完。
做法是位移只花「自己走得完」的时间（按真实步速），**到得早就地站着等下一段**：

- 演示倍率 `behaviorTimeScale`：60 → **20**（一天走完约 72 分钟；单次进食约 1.5 秒起）
- 步速 `walkSpeedMps`：0.45 → **0.3 m/s**（3 m 横穿约 10 秒，看得出走路）
- 位移动画时长上限 `maxTravelAnimS`：**12 秒**（样板间对角线上限）
- 进食/饮水/用砂盆的**出现频率**提到约 1.6–2.4 倍（时段偏好不变），
  单次片段 **45–150 秒**，权重上调后仍远低于静息与高处停留

**一处自己踩的坑值得记下**：第一版把动画时长写成
`max(自然所需时间, 时间线片段时长 × 6)`，本意是「拖慢到看得清」，
结果在时间线里存在的长移动段（600 秒）上算出 **3600 秒**的慢动作走路，比瞬移更糟。
现在上限由**真实几何**封顶，绝不让长片段决定动画时长。

**吃 / 喝 / 用砂盆三件事怎么在画面上分开**：三者的姿势都是《蹲伏》，
光靠姿势无法区分——这本身也是「看不到它们在做什么」的原因之一。
因此新增 `ACTIVITY_MOTION` 配方，只改头部与重心的微动作：
进食是低头小幅快速咬取（2.2 Hz）、饮水是更低更快的舌部动作（4.2 Hz）、
用砂盆是前后重心移动（1.1 Hz）。配方数值是操作化常量，不是文献数字。

**突发演示不乘倍率**（同一类坑的第二次踩中）：`demoDurationS` 本身已经是
「给人看的真实秒数」（「僵直不动」的十分钟量级被压缩成 60 秒）。若再乘一次 20× 倍率，
一次 15 秒的抽搐只渲染 **0.75 秒**——用户点下去几乎看不到东西。
因此行为运行时对**带 `incidentKind` 的区间按真实时间推进**，其余区间仍按倍率推进节律。
契约由单测钉住（`demoDurationS` 必须落在 10–120 秒）。

**诚实边界**：这些改动全部是**演示可读性**取舍，写进了 `OPERATIVE_CONSTANTS`
并逐项说明理由；文献给出的是这些行为的**日周期形状**（进食双峰 04–08 / 16–20、
砂盆 04–08 / 20–24），**没有给**「一天占多少比例」，所以提高出现频率不等于宣称真实占比。

## 9. 明确不做

- 不做情绪识别、不做疼痛/恐惧判别。突发演示只演示**动作**，不输出「它怎么了」的结论。
- 不做声音播放，也不做声音语义翻译（既有硬约束 3.2）。
- 不做多猫互动：猫-猫互动率（0.58 次/猫/小时）来自**猫咖**人群，不适用本项目。
- 不做真实寻路算法（见 §7 的已知限制）。
- 不把 `unverified` 参数变成数字（每日跳数、活动片段数/时长、最大跳跃高度、抓挠单次时长）。
- 不新增生理通道的精度宣称：呼吸与心率仍标注「未取得猫用项圈验证研究」。
